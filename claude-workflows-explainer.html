Claude GitHub Workflows

two reusable workflow_call pipelines — a comment-driven reviewer and a human-approval gate

What changed in claude-pr-review.yaml

  • The first review is comment-triggered: comment ai review on a PR to summon the full multi-lens review (phrase configurable via TRIGGER_PHRASE).
  • Removed: automatic run on pull_request opened / reopened / base-retarget.
  • Opt-in auto re-review: once a PR has an ai review comment, each new commit (synchronize) auto-runs the incremental re-review. PRs nobody asked to review are left alone.
  • A small check-optin job scans the PR's comments for the trigger phrase and gates the re-review job via needs.
  • Kept: the @claude comment-trigger job for general ad-hoc questions.
  • New step checks out the PR head (gh pr checkout) since comment events default to the base branch.

1. Claude PR Review claude-pr-review.yaml

A reusable workflow the calling repo wires to issue_comment, pull_request_review_comment, and pull_request (synchronize) events. A comment is routed by content: ai review starts a structured multi-lens review of the PR head, @claude runs a lightweight general assistant. A new commit triggers an auto re-review, but only if the PR was previously opted in with an ai review comment.

Why opt-in? The first review only runs when a human asks (ai review), so untouched PRs cost no model time. But once a PR is opted in, each new commit auto-re-reviews it — the check-optin job enforces that gate. concurrency is keyed per PR number, so a newer ai review or push supersedes an in-flight run instead of stacking duplicates. Model traffic stays on Bedrock via OIDC — no API keys in the steps. The @claude branch is a separate general-assistant job, independent of the review path.
BOT_LOGIN_PATTERN — re-review only. A jq regex the re-review job uses to find its own previous review among all the PR's reviews (.user.login | test(pattern)), so it knows whether it last said CHANGES_REQUESTED (verify those findings) or APPROVED (lightweight review), and can read that review's body + commit SHA. Default (?i)^github-actions(\[bot\])?$ matches the github-actions[bot] account the workflow posts as when using the default GITHUB_TOKEN. You don't need to set this — only override it if reviews run under a dedicated GitHub App with a different login. If it matches nothing (or the first review hasn't posted yet), re-review safely falls back to a full review.

2. Human Approval Gate claude-human-approval-gate.yaml

Keeps a required commit status (Claude / human-approval-required) current so a bot approval can never merge any PR. Branch protection requires this status; the bot never grants the human approval that satisfies it. It re-evaluates on every review event and on PR open/reopen/synchronize.

Now always-on — bot approval is never sufficient

  • Removed: the requires-human-review label opt-in (and the GATE_LABEL input). PRs no longer default to success when unlabeled.
  • Every PR now requires ≥ 1 human APPROVED review to reach success. No human approval → failure → merge blocked.
  • Reviews authored by bots/apps (user.type == "Bot", e.g. the Claude reviewer posting as github-actions) are filtered out, so a bot APPROVE never counts.
  • Runs on PR opened/reopened/synchronize too, so the required check starts out failing and re-attaches to each new HEAD commit — you can't merge until a real human approves.

How they fit together. The reviewer posts findings and a verdict for extra signal, but it can never merge anything on its own: the gate applies to every PR and blocks merge until a real human submits an APPROVED review. The bot's own approval is filtered out by user.type != "Bot", so a wrong bot APPROVE is never sufficient — which is what makes a blocking AI review safe.

3. Bedrock setup & required IAM runner role · SRE/DevOps

Both workflows are model-on-Bedrock only. Each run authenticates with GitHub OIDC, assumes the runner role arn:aws:iam::833328140030:role/gha-runner-role-us-east-1, and calls the model in us-east-1 through the US cross-region inference profile us.anthropic.claude-sonnet-4-6 (routes to us-east-1 and us-west-2). Three things must be in place, all owned by SRE/DevOps.

1. IAM invoke policy on the runner role

Two statements: the first lets the role call the inference profile; the second lets the profile invoke the underlying foundation model in each region it can route to. Omitting the second statement is the usual cause of AccessDeniedException even when the profile call looks allowed. InvokeModelWithResponseStream is required because the action streams.

{ "Version": "2012-10-17", "Statement": [ { "Sid": "InvokeClaudeInferenceProfile", "Effect": "Allow", "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"], "Resource": "arn:aws:bedrock:us-east-1:833328140030:inference-profile/us.anthropic.claude-sonnet-4-6" }, { "Sid": "InvokeClaudeFoundationModelsInRoutedRegions", "Effect": "Allow", "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"], "Resource": [ "arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-sonnet-4-6", "arn:aws:bedrock:us-west-2::foundation-model/anthropic.claude-sonnet-4-6" ], "Condition": { "StringLike": { "bedrock:InferenceProfileArn": "arn:aws:bedrock:us-east-1:833328140030:inference-profile/us.anthropic.claude-sonnet-4-6" } } } ] }

2. Enable Bedrock model access (account-level, separate from IAM)

In the Bedrock console → Model access, grant access to Anthropic Claude Sonnet 4.6 in us-east-1 and us-west-2. Without this, invoke fails regardless of the IAM policy above.

3. OIDC trust must cover the calling repos

These are reusable (workflow_call) workflows invoked from other repos with secrets: inherit. When a reusable workflow runs, the OIDC token's claims reflect the calling repo, not shared-workflows. Confirm the role's trust policy permits those repos:

{ "Effect": "Allow", "Principal": { "Federated": "arn:aws:iam::833328140030:oidc-provider/token.actions.githubusercontent.com" }, "Action": "sts:AssumeRoleWithWebIdentity", "Condition": { "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" }, "StringLike": { "token.actions.githubusercontent.com:sub": "repo:FootprintRecreation/*" } } }

Smoke test (run as the role in us-east-1)

aws bedrock-runtime invoke-model \ --region us-east-1 \ --model-id us.anthropic.claude-sonnet-4-6 \ --body '{"anthropic_version":"bedrock-2023-05-31","max_tokens":16,"messages":[{"role":"user","content":"ping"}]}' \ /dev/stdout
Confirm before shipping. The exact inference-profile ID (us.anthropic.claude-sonnet-4-6) should be verified with aws bedrock list-inference-profiles --region us-east-1 — some IDs carry a -vN:M suffix, and a wrong ID both breaks the workflow and mis-scopes these ARNs. The base model ID must match the MODEL input default in claude-pr-review.yaml.
